# Asset search requirements

This document records the agreed requirements for the `asset_search` inspection tool. Numeric traversal thresholds will be determined through implementation profiling.

Responses follow the shared [inspection output requirements](inspection-output.md): YAML in a single MCP text-content block on success, or an error message with MCP `isError` on failure.

## Agreed requirements

### REQ-013: Search assets

The MCP server must provide an inspection tool to search assets in the configured project's Unreal environment. It must be available without `--writable`.

The tool must support searching assets by:

- Asset name mask.
- Base class.
- Asset references in both directions: incoming references ("used by") and outgoing references ("using") relative to a specified asset.

### REQ-014: Direct and transitive reference search

Reference search must support both direct references and transitive reference chains in either direction. Direct reference search is the default; an explicit transitive-search option enables traversal beyond immediate references.

The tool's description of the transitive-search option must warn that results may be large or truncated. If a search result is truncated, the response must explicitly report that it is incomplete rather than present it as the complete result set. Traversal limits follow REQ-026; result pagination follows REQ-021.

### REQ-015: Combine search filters with AND

The asset-search tool must allow name-mask, base-class, and reference filters to be supplied together. Every returned asset must satisfy all supplied filters (logical AND). An omitted filter imposes no restriction of that type.

For example, a search may request assets whose names match `BP_*`, whose classes match a specified base class, and which match a specified reference relationship. Only assets satisfying all three conditions may be returned.

### REQ-016: Simple asset-name wildcards

Name-mask search must use case-insensitive wildcard matching against the asset name, rather than its full package or object path:

- `*` matches any sequence of characters, including an empty sequence.
- `?` matches exactly one character.

The mask matches the whole asset name. A mask without wildcards therefore matches an exact name, ignoring case; `*Door*` matches names containing `Door`. The mask is not a regular expression.

### REQ-017: Native and Blueprint base-class matching

The base-class filter must accept native Unreal classes and Blueprint classes. It must match the specified class and its descendants, including indirect descendants.

For Blueprint assets, matching must use the class represented/generated by the Blueprint rather than merely the asset's storage class. For example, an Actor base-class search must find Actor-derived Blueprints, and a Blueprint base-class search must find Blueprints derived from that Blueprint class.

Requests identify native classes by their full class paths and Blueprint classes by their full generated-class paths, as specified in REQ-023.

### REQ-018: Three asset-search scope levels

The asset-search tool must offer three selectable scope levels:

| Scope level | Included content |
| --- | --- |
| 1 | `/Game` only. |
| 2 | `/Game` and content from project-local plugins. |
| 3 | `/Game`, Engine content, and content from all plugins available to the configured project. |

Project-local plugin content must be distinguished from engine-installed plugin content. Scope levels describe Unreal asset content available in the configured project's editor environment, rather than arbitrary filesystem searches.

Level 2 (`/Game` and project-local plugin content) is the default when scope is omitted. The request parameter `scope` uses the integer values 1, 2, and 3 for these levels.

### REQ-019: Result scope preserves transitive reference chains

The selected search scope must limit returned assets, not reference traversal. A transitive search may traverse assets outside the selected scope when following reference chains, while returning only assets within the selected scope that satisfy all supplied filters.

For example, if A references B and B references C, and only A and C are within the selected scope, an outgoing transitive search from A must still be able to find C through B. B must not appear in the returned asset list. The same rule applies to incoming traversal.

Traversal remains within content available to the configured project's editor environment and is subject to the search limits and explicit truncation reporting.

### REQ-020: Saved reference evidence only

Reference search must use saved hard and soft asset references. It must not include unsaved in-memory reference changes or implicitly save assets to refresh reference evidence. This applies to both reference directions and to every step of transitive traversal.

The tool description and results must make clear that reference matching reflects saved content, which may differ from the current unsaved editor state. Asset-management relationships and searchable-name dependencies are outside this initial reference-search scope.

### REQ-021: Stateless pagination by page size and index

The asset-search tool must support pagination through `page_size` and zero-based `page_index` parameters. The offset is `page_index * page_size`: skip that many matching assets and return up to `page_size` subsequent matches.

Pagination must not depend on retained search results, pagination sessions, or continuation cursors. Each page request must be independently evaluable using its search filters, scope, and pagination parameters.

Filtering must occur before pagination. Matching assets must be sorted by full asset path in ascending order before the offset is applied. For complete search evaluations over unchanged searchable data with identical filters, scope, and page parameters, page membership must be repeatable. Truncated evaluations have the limitations described in REQ-026.

Stateless pagination does not preserve a snapshot across requests. If searchable data changes between page requests, page boundaries may shift, producing repeated or missed assets across those requests; the tool documentation must describe this behavior.

`page_size` defaults to 100 and has a maximum of 1,000. It must be a positive integer. `page_index` defaults to 0 and must be a nonnegative integer.

### REQ-022: Selectable search-result detail

The asset-search tool must accept a `details` parameter with two values:

- `brief` (default): return the asset matches as a list of full asset object-path strings, such as `/Game/Actors/BP_Door.BP_Door`, without per-asset metadata records. Do not return bare asset names.
- `metadata`: return asset records containing paths, class names, parent classes where applicable, and other agreed metadata.

The detail level changes how matches are represented, not which assets match, their order, or pagination. Required completeness and truncation reporting must remain available in both modes.

Each `metadata` record uses the following fields, subject to the applicability and availability rules below:

| Field | Meaning |
| --- | --- |
| `path` | Full asset object path, using the same representation as `brief`. |
| `name` | Asset name. |
| `asset_class` | Full identifier of the asset's storage class. |
| `generated_class` | Full identifier of the class generated by a Blueprint asset; applicable to Blueprint assets. |
| `parent_classes` | Inheritance chain as full class identifiers, nearest parent first. For Blueprint assets, use the generated class's ancestry; for other assets, use the asset class's ancestry. |

`parent_classes` must not include the class itself.

Metadata values must distinguish inapplicable, unavailable, and known-empty data:

- Omit fields that do not apply to the asset, such as `generated_class` for a texture.
- Use `null` for an applicable value that is unavailable, with an explanation in the response's `warnings` list. Do not invent unavailable metadata.
- Use `[]` for `parent_classes` when the inheritance chain is known to be empty. Do not use an empty list to represent an unknown chain.

### REQ-023: Asset-search tool name and request structure

The public tool name must be `asset_search`. Its request fields are:

| Field | Type | Required/default | Meaning |
| --- | --- | --- | --- |
| `name_mask` | string | Optional | Case-insensitive asset-name wildcard filter. |
| `base_class` | string | Optional | Full native class path or Blueprint generated-class path; includes descendants. |
| `reference` | object | Optional | Reference filter described below. |
| `scope` | integer: 1, 2, or 3 | Default: 2 | Content scope for returned assets. |
| `details` | string: `brief` or `metadata` | Default: `brief` | Per-asset result representation. |
| `page_size` | integer, 1–1,000 | Default: 100 | Maximum asset matches returned for the requested page. |
| `page_index` | nonnegative integer | Default: 0 | Zero-based page index. |

When `reference` is supplied, it contains:

| Field | Type | Required/default | Meaning |
| --- | --- | --- | --- |
| `asset` | string | Required | Full asset object path anchoring the reference search. |
| `direction` | string: `using` or `used_by` | Required | Direction relative to `reference.asset`. |
| `transitive` | boolean | Default: `false` | Follow reference chains beyond direct references. |

`using` returns assets that `reference.asset` references (outgoing dependencies). `used_by` returns assets that reference `reference.asset` (incoming referencers). In transitive mode, apply the selected direction throughout traversal.

The three filters (`name_mask`, `base_class`, and `reference`) are optional and combine with AND. Native class paths use the form `/Script/Engine.Actor`; Blueprint generated-class paths use the form `/Game/Actors/BP_Base.BP_Base_C`.

Example request:

```json
{
  "name_mask": "BP_*",
  "base_class": "/Script/Engine.Actor",
  "reference": {
    "asset": "/Game/BP_Main.BP_Main",
    "direction": "using",
    "transitive": false
  },
  "scope": 2,
  "details": "brief",
  "page_size": 100,
  "page_index": 0
}
```

### REQ-025: Asset-search YAML result envelope

Successful `asset_search` responses must use this YAML envelope in the MCP text-content block:

```yaml
items:
  - /Game/Actors/BP_Door.BP_Door
page_size: 100
page_index: 0
total_matches: 1
has_more: false
truncated: false
warnings: []
```

| Field | Meaning |
| --- | --- |
| `items` | Requested page of full asset object-path strings in `brief` mode or asset records in `metadata` mode. |
| `page_size` | Effective page size used for this request. |
| `page_index` | Effective zero-based page index used for this request. |
| `total_matches` | Total matching assets before pagination, or `null` when unknown. |
| `has_more` | Whether another page of matches exists after this page, or `null` when that cannot be determined. |
| `truncated` | Whether limits prevented complete search evaluation. Ordinary pagination alone must not set this to true. |
| `warnings` | Messages explaining incomplete search results or unavailable metadata; an empty list when there are no warnings. |

The example shows a complete search with one match. Unknown counts or continuation status must not be represented as an exact count or `false`. Search-limit truncation and unavailable per-asset metadata must be described accurately in warnings.

### REQ-026: Bounded reference traversal

Reference traversal must enforce server-controlled limits on visited assets, examined references, and execution time. Numeric thresholds must be chosen through implementation profiling rather than fixed arbitrarily in these requirements.

When any traversal limit is reached, stop traversal and return the available matching assets for the requested page with `truncated: true` and an explanatory warning identifying the limiting condition. Apply all result filters, sort by full asset path, and paginate the collected matches as usual. Do not report partial collected-match counts as exact totals; use `null` for `total_matches` or `has_more` when their values cannot be established.

A truncated evaluation may discover only a subset of matches. Time-limited evaluations may collect different subsets across requests even when asset data is unchanged. Warnings must make clear that pagination over truncated evaluations does not guarantee complete or repeatable coverage; requesting a later page does not resume an interrupted traversal.

## Implementation follow-up

- Profile representative projects to choose limits for visited assets, examined references, and execution time.
